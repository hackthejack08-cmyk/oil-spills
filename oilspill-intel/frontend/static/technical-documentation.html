Oil-spill intelligence,
from observation to review.

A suspected slick has appeared offshore. Where was it observed, where might it move, and which vessels need investigation?

OSI brings radar imagery, drift estimates and historical vessel tracks into one investigation view. The response brief turns those results into a readable handoff for a Coast Guard, port or pollution-response officer.

Technical documentation · 26 September 2026 · Prototype implementation

The public site combines live catalogue previews with a saved, labelled demonstration. It is not an operational surveillance service. A catalogue image is not automatically a detected oil spill.

1. Problem and scope

A dark feature on radar is only a starting point. An investigator must establish its location and observation time, consider look-alikes, reconstruct possible movement and inspect traffic near plausible release locations.

The problem we address is the work needed to connect these steps and explain the result. OSI keeps scene identifiers, timing, candidate geometry, model assumptions and vessel evidence together. It does not establish legal responsibility or replace field confirmation.

Satellite oil-spill monitoring, drift modelling and vessel correlation already exist. EMSA CleanSeaNet combines these capabilities operationally. Our contribution is a small, inspectable implementation with multiple release-time hypotheses, visible evidence gaps and a handoff brief—not a claim to have invented the overall workflow.

3. Processing workflow

  1. Locate the scene
    Area, acquisition time, source ID
  2. Screen the radar image
    Candidate polygons and look-alike checks
  3. Retrieve environment
    Time-matched wind and currents
  4. Estimate drift
    Possible origins and future movement
  5. Compare vessel tracks
    Evidence-ranked investigation leads
  6. Review and hand off
    Response brief and evidence record

Radar screening

The baseline smooths SAR backscatter, compares each pixel with its local background and applies a contrast-based score. Morphological filtering joins neighbouring pixels; connected regions become candidate slicks. Geometry and look-alike checks assess contrast, shape and coastal context. A dark patch can also be calm water, wind shadow or another non-oil feature.

GIS: putting the evidence in the same place

GIS means Geographic Information System. Here it connects the raster's coordinate reference system with slick polygons, current grids and AIS tracks. Rasterio reads georeferenced images; PyProj handles coordinate transformations; Shapely supports geometry operations; Leaflet displays the map. Distances and areas must be calculated with geographic coordinates accounted for, not from screen pixels.

Drift and release hypotheses

The built-in surface-particle model combines currents, a wind-driven component and stochastic spreading. Backward runs test several possible release ages; forward runs estimate movement from the observation. The output is a collection of possible positions and a time window. It is not a measured release instant. OpenDrift is an optional adapter, not the engine used by the saved baseline demonstration.

Vessel evidence

Historical AIS tracks are compared with the origin hypotheses using spatial proximity, timing, track orientation, behaviour and data quality. Weighted rules produce a ranking. Gaps and inferred positions remain visible. A score of 75/100 means an uncalibrated evidence-match score—not 75% accuracy or a 75% probability that the vessel caused pollution.

Replay versus reception

The measured example was acquired on 16 June 2019, from 14:07:38 to 14:08:03 UTC. Its 25-second animation illustrates a product acquisition interval; it is not a recording of satellite downlink. Replay speed changes presentation timing only. Display enhancement does not add measured resolution and does not replace the detector's input with AI-upscaled pixels.

The public catalogue query currently covers the Mumbai coast, 72.2–73.0° E and 18.6–19.5° N. This is a configured demonstration area, not a limitation of satellite physics. The separate synthetic scenario and archived measured sample are labelled with their own coordinates and dates.

5. Response brief: the user-facing addition

An officer should not have to assemble a handoff from several technical panels. After results arrive, the Home view shows the observation time and location, selected candidate area, possible release window, movement estimate and highest-ranked vessel lead.

Copy brief and Download brief produce the same plain-text summary. Checks include missing drift or AIS results, expired forecast periods, uncertain AIS positions and synthetic-data warnings. Changing the selected detection cannot pull in another detection's drift or vessel results.

The brief does not calculate coastal arrival time, choose a response vessel or dispatch an alert. Those decisions need validated forecasts, exposure data and agency procedures. This feature addresses a practical handoff need; it has not yet been evaluated with operational users.

6. Measured results

The packaged diverse baseline run contains 19 usable scenes: 10 oil-positive and 9 look-alike examples. One requested negative had no matching indexed scene and was excluded. A hit requires a candidate score of at least 0.50 within 8 km of the labelled point.

MeasureResultMeaning
Recall8/10 = 80.0%Two positive cases were missed.
Negative false-alarm rate4/9 = 44.4%Four look-alikes generated a positive result.
Precision8/12 = 66.7%Share of positive predictions that matched positive labels in this test.
Scene-level accuracy13/19 = 68.4%Eight true positives and five true negatives; not pixel accuracy.

The false-alarm rate is too high to treat the baseline as an unattended operational detector. These are small-sample screening results, not a deployment-wide accuracy claim. Forecast error, calibrated uncertainty and vessel-attribution accuracy remain unmeasured.

The ten-image download is a subset for inspection, with five positive and five negative chips. It is not the full 19-scene denominator above. Its manifest includes expected labels and baseline outcomes, including mistakes.

7. Testing the public build

  1. Open the application and select Scan for oil spills. The data badge must say Demo data. This runs the saved synthetic workflow.
  2. Wait for all stages to finish. In the current sample, one candidate passes the public review filter, its area is 14.20 km² and SYN-TANKER-ALPHA is the highest-ranked lead at 75/100. These are reproducibility checks, not real incident claims.
  3. On Home, read the Response brief. Expand Checks before handoff. Verify that the synthetic warning and 39-minute AIS-gap limitation are present. Copy the brief and download its text file.
  4. Open Evidence, inspect the record and use Download report for JSON. A SHA-256 hash helps detect changes to a record; it does not prove the scientific result or give legal certification.
  5. Open Accuracy and download the labelled test pack. Check positive and negative examples against its manifest. Running fresh detection on these arbitrary TIFFs requires the local backend.
  6. Select View latest real radar image. Check its source, coordinates and acquisition time. A preview must say analysis is pending and must not retain the synthetic case's vessel ranking. If the live catalogue is unavailable, the bundled 2019 measured scene is used and must remain labelled historical.
  7. For upload replay, download Download test image from Home and select that exact file. Other images must report the public-build limitation instead of borrowing its detection result.

Before recording a demonstration, test the public link in a signed-out browser. Keep catalogue connectivity and a recorded scenario separate in your narration. Record only results you can reproduce.

8. Engineering and local execution

The interface is HTML, CSS and JavaScript with Leaflet. The public deployment serves static assets plus a catalogue-preview endpoint. The analysis service is Python/FastAPI with Pydantic validation. Rasterio, NumPy/SciPy, PyProj, Shapely and xarray support raster, geometry and environmental processing. SQLite stores the prototype's records; geometries use GeoJSON. PostGIS is an upgrade option, not the current database.

From the repository's oilspill-intel directory:

python app.py
# Opens the local service at http://localhost:8000

node tools/check_response_brief.cjs
python tools/check_public_demo.py
cd backend
..\.venv\Scripts\python.exe -m pytest tests -q

The pytest command above is for Windows; on Linux/macOS use ../.venv/bin/python -m pytest tests -q from backend. Run tests there so Python imports the backend package rather than the root launcher. The launcher can install dependencies; real-data runs also need network access and appropriate source credentials. See the installation guide. Never publish credentials in a presentation, repository or browser bundle.

9. Limits and the next validation steps

  • Reduce false alerts: evaluate on a larger incident-separated set with wind shadows, calm water, coastal features and other hard negatives. Train and test any learned model on separate incidents; report misses as well as hits.
  • Validate drift: compare forecasts with later observed slick positions or suitable drifter records. Report position error by forecast horizon and how often observations fall inside the predicted region. Synthetic agreement is not enough.
  • Check attribution: use authorised historical AIS and independently documented incidents. Sparse, switched-off or incorrect AIS can prevent identification.
  • Handle different observations: EO may be cloudy, delayed or too coarse. A single SAR scene does not reveal a unique spill age. Missing metadata must produce a partial result, not invented inputs.
  • Prepare deployment: add access control, upload limits, retention rules, service health monitoring and a persistent job scheduler before operational use. No continuous-service uptime guarantee is made for this prototype.
